## Q1. Surfaces per framework, and which are distinct code paths

Exports map (packages/ui/package.json, `exports`):

- `"."` -> `browser`/`default` `./dist/index.js`, `node`/`worker`/`deno` `./dist/index.server.js`. SolidJS barrel,
  per-module output. Source entry `src/index.ts`.
- `"./solid"` -> `./dist/solid.js` / `./dist/solid.server.js`. Superset of `"."`; `src/solid.ts:35` is
  `export * from './index';` then the extra Solid-only exports. Own build targets (config/vite/lib.ts TARGETS
  `solid`, `solid.server`, both `perModule: true`).
- `"./react"` -> `./dist/react.js` (no condition split). Generated typed wrappers.
- `"./web-components"` -> `./dist/kai.es.js`. Register-all facade.
- `"./web-components/*"` -> `./dist/web-components/*.js`. One self-registering module per tag basename.
- `"./autoloader"` -> `./dist/web-components/autoloader.js`.
- `"./state"`, `"./wire"`, `"./stores"`, `"./define"`, `"./diagnostics"`, `"./schemas"`, `"./construct"`,
  `"./provider"`: separate targets, aggregate (not per-module) by contract (config/vite/lib.ts, the note above
  `TARGETS` says state/wire/stores stay aggregate because verify-cdn-entries promises them self-contained).

Distinct code paths, stated plainly:

1. React: ONE distinct path. `frameworks/react/index.tsx` (auto-generated by scripts/gen-web-component-api.mjs)
   imports only `./runtime` + `react` and registers each element LAZILY:
   `frameworks/react/index.tsx:141` `() => import('@kitn.ai/ui/web-components/agent-card')`, one per wrapper
   (95+ literal specifiers, all present in `dist/react.js` as literal `@kitn.ai/ui/web-components/<basename>`
   strings). `frameworks/react/runtime.tsx:92` is the register-all fallback for `registerAll()`:
   `registerAllLoad ??= import('@kitn.ai/ui/web-components')`. So React reaches the SAME custom elements as the
   web-component consumers, only through a per-element lazy import, and only if the consumer uses the wrappers.
2. SolidJS: TWO entries, one source tree. `"."` is the minimal barrel (what React/Vue/Svelte/vanilla consumers
   who import `@kitn.ai/ui` get); `"./solid"` is `"."` plus the Layer 2/3 Solid-only components
   (`src/solid.ts:35` is `export * from './index';`, then the extra exports). `dist/solid.js` is standalone: no
   runtime dependency on `dist/index.js`.
3. Vue / Svelte / Angular / plain HTML: ONE code path, FOUR users. All four consume the same `kai-*` custom
   elements. Per framework there is no generated binding in this package: `frameworks/` holds only `react/`
   (`ls packages/ui/frameworks` -> `index.tsx`, `runtime.tsx`, `use-kai-chat.tsx`, `use-voice-input.tsx`).
   Vue/Svelte/Angular/HTML each get one of two delivery modes and nothing else:
   - per-element: `import '@kitn.ai/ui/web-components/<basename>'` (tree-shakeable, node_modules path),
   - register-all: `import '@kitn.ai/ui/web-components'` (one facade + one big lazy chunk),
   - or the autoloader `<script type="module">` (CDN only, see Q4).
   So the answer to "one code path or four": one element-registration code path, four consumer-side wrappers of
   it, and the wrappers are the consumer's own (Vue `defineCustomElement` adapter, Angular `CUSTOM_ELEMENTS_SCHEMA`,
   Svelte `onMount` + property assignment, plain HTML). Nothing in this package branches per framework except
   `./react`.

Recommendation: state this in the docs as "three shipped runtime paths: React wrappers, Solid barrels, web
components; four framework consumers of the third". No code change.

## Q3. Does one facade import shake the rest? (read off the existing dist/)

Layout: `dist/` root has 145 top-level `.js`; `dist/web-components/` has 95 `.js` (94 facades +
`autoloader.js`). Facade modules are the OUTER files (`dist/web-components/chat.js`), and the same basename
also exists as a DIRECTORY holding only declarations (`dist/web-components/chat/chat-types.d.ts`, etc.) -
that is the barrel dts emit, not a second JS output.

The two receive-sets for a consumer:

- `import '@kitn.ai/ui/web-components'` -> `dist/kai.es.js` = 31,856 B (facade + Solid runtime + registry
  helpers) and it dynamically imports `dist/register-impl-BGBoKNUy.js` = 761,383 B. So the register-all path
  costs ~31.8 KB eager and ~761 KB more when the promise resolves. `kai.es.js` also carries a tag->module map
  (`Un` object in the file) and the `webComponentsReady` promise.
- `import '@kitn.ai/ui/web-components/chat'` -> `dist/web-components/chat.js` = 23,623 B plus its STATIC
  closure. NOT `register-impl-*`. Measured static closure (relative `./`/`../` specifiers only, transitivity
  included), from the existing dist:

  | facade | files in static closure | raw bytes | lazy `import(...)` chunks |
  |---|---|---|---|
  | `web-components/chat.js` | 95 (1 facade + 94 shared chunks) | 563,238 | 13 |
  | `web-components/message.js` | 73 | 449,826 | 13 |
  | `web-components/thread.js` | 75 | 457,014 | 13 |
  | `web-components/button.js` | 36 | 189,808 | 0 |
  | `web-components/loader.js` | 4 | 170,251 | 0 |
  | `web-components/agent-card.js` | 6 | 168,051 | 0 |
  | `web-components/markdown.js` | 9 | 216,411 | 13 |

  Largest single shared file in every closure: `dist/define-BdZXGfXZ.js` = 148,633 B (Solid runtime +
  `defineWebComponent` + diagnostics). `dist/cn-DgkUffdp.js` = 13,872 B. The 13 lazy chunks are the shiki
  grammars/themes + `core-AYMC6_lb.js` + `engine-javascript-*` (imported dynamically, so not in the eager set).

So the answer to "is the shared chunk set reachable from one facade": YES, and it is the design. 94 of the 145
top-level chunks are reachable from `chat.js` alone. The per-module build is doing its job ONLY in the sense
that the 761,383 B register-impl aggregate is NOT among them - a facade gets the shared primitives it needs and
never the aggregate. It is NOT doing per-facade isolation: `button` (189,808 B) and `agent-card` (168,051 B)
both land near the same ~170 KB floor because `define-BdZXGfXZ.js` alone is 148,633 B. What a CONSUMER's
bundler then keeps is smaller, because whole modules drop when their exports are unused (this is the measured
13,858 B `cn` probe against a 563 KB graph). The raw closure above is the source-level reach, NOT the shipped
bytes; the shipped bytes for a facade are exactly what no probe measures today (Q2).

Recommendation: add the `wc-chat-eager` / `wc-loader-eager` probes from Q2 before believing any further
per-facade claim. A ratio between them (`button` floor vs `chat` closure) is the readable signal for "did
per-module output stop working", and it is the number this lane could not produce without a build.

## Q4. CDN / autoloader path: what is asserted, what is not

Mechanism (verified by reading, not assumed):

- `src/web-components/autoloader/autoloader.ts:21` `const tagToModule = manifest.tags;`
- `autoloader.ts:28` `const BASE = import.meta.url.slice(0, import.meta.url.lastIndexOf('/') + 1);` with the
  load-bearing comment that it is string ops on `import.meta.url` on purpose, NOT
  `new URL('./x', import.meta.url)` (Vite rewrites that into a static-asset glob).
- `autoloader.ts:38` `await import(/* @vite-ignore */ \`${baseOverride ?? BASE}${file}.js\`)`.
- `setAutoloaderBasePath` (line 32) is the only override; `startAutoloader` (line 72) is the only entry.

THE BASENAME QUESTION, VERIFIED. `src/web-components/web-component-manifest.json` `tags` is
96 entries `{ 'kai-chat': 'chat', ... }`; every value is a BASENAME with no `/`
(`node -e` over the committed manifest: `any file value with slash? 0`, `files with slash? 0`). The split
build (`config/vite/web-components.ts` `splitConfig`) resolves each manifest file key by a recursive walk of
`src/web-components/` with a duplicate-basename throw, and emits `entryFileNames: 'web-components/[name].js'`
with `[name]` the manifest key. So `dist/web-components/autoloader.js` has `BASE` =
`<...>/dist/web-components/` and resolves `<...>/dist/web-components/chat.js` - the family folders under
`src/` are invisible to the runtime lookup. Folding the layer into folders cannot move a basename, so the
autoloader is unaffected. That is confirmed rather than assumed (manifest values + `[name]` + `BASE`
all read directly).

What IS asserted today:

1. `scripts/verify-web-components-bundle.mjs` (`verify:web-components-bundle`, runs in `build`) - build-time
   only, and about the REGISTER-ALL entry: (a) `dist/kai.es.js` still references `register-impl`;
   (b) every relative dynamic `import("./x.js")` it makes that carries >= 5 kai-* tag literals is covered by
   a `package.json` `sideEffects` glob. Has a `--self-test` with 11 synth cases (both defects planted
   separately and together, plus vacuity, missing chunk, boolean sideEffects, no-tags manifest, missing
   bundle). It does NOT touch the autoloader.
2. `scripts/verify-consumer-sideeffects.mjs` entry A/B (Q2) - consumer-side, per-element and register-all,
   tag literals must survive a real Vite 8 bundle. Does NOT touch the autoloader.
3. `scripts/verify-cdn-entries.mjs` (`verify:cdn-entries`, `postbuild`, CI) - `SELF_CONTAINED_ENTRIES =
   ['state.js', 'wire.js', 'stores.js']` must carry ZERO bare specifiers (a raw-URL page must not throw
   "Failed to resolve module specifier"). Self-test plants bare `import "solid-js"`, a bare dynamic import,
   and a missing entry; and fails if the extractor matches zero specifiers. The list is a CONTRACT
   declaration, deliberately not derived. The autoloader is NOT in the list (it is self-contained by build,
   but nothing asserts that).
4. `src/web-components/autoloader/autoloader-walk.test.ts` - unit tests for the WALK only
   (`<template>` content, root element, nested template, unknown tags) plus one surface test that
   `@kitn.ai/ui/autoloader` exports exactly `setAutoloaderBasePath` + `startAutoloader` and that
   `scripts/gen-web-component-dts.mjs` declares the same two names. It imports `./autoloader` in jsdom, so it
   exercises `customElements.get`, not the fetch.
4b. THE PRECEDENT THAT DOES NOT EXIST FOR THE AUTOLOADER: `scripts/verify-react-wrappers.mjs` (runs inside
   `build`) asserts every per-element specifier in `dist/react.js` resolves to an existing
   `dist/web-components/<X>.js`, and that the bundle opens with `'use client'`. Its header says exactly why
   (a specifier whose file does not exist 404s and the element silently never registers). The autoloader's
   `BASE + file + '.js'` is the same class of fact with no equivalent check; React gets one, the autoloader
   does not. Note both build-time guards are inside the NX-cache-skippable `build` (CLAUDE.md's build caveat).
5. The real end-to-end exercise, and the one that would actually catch a broken BASE resolution:
   `verify:blocks` (`scripts/verify-blocks.mjs`, CI `.github/workflows/test.yml:1213`). Its `[driver]` check

   `/kit/web-components/autoloader.js` (e.g.
   `scripts/block-driver/pages/generated/support-widget/index.html:375`,
   `.../assistant/index.html:287`, `.../in-app-assistant/index.html:375`,
   `scripts/block-driver/pages/kai-chat-facade/index.html:37`). The driver enforces zero console

   uses. So a BASE/tag->module regression shows up as the autoloader's own
   `[kai-autoloader] could not load ...` warning, or as a hang. This IS the proof the task asks whether
   anything has - it exists, indirectly, via the blocks gate.

What is NOT asserted:

## Q5. Cheapest concrete checks to add, ranked

1. `scripts/verify-consumer-sideeffects.mjs` EAGER_PROBES: add `wc-chat-eager` and `wc-loader-eager`
   (browser, `import '@kitn.ai/ui/web-components/chat'` / `.../loader'`). Cheapest, highest value: it is the
   only place a real bundler weighs what the per-element path costs, and the mechanism already exists. Also
   extend the trace plugin's recorded specifiers + `CONDITION_EXPECTATIONS` (Q2 note).
2. Same file: add `react-button` (browser) and `solid-thread` (browser) probes. Closes the exact list
   section 6 of docs/handoff/2026-09-18-src-ui-merge-and-footprint.md names as the "cheapest next win".
3. `scripts/verify-cdn-entries.mjs`: add `web-components/autoloader.js` to `SELF_CONTAINED_ENTRIES`. One line.
   Cheap but weak (4,233 B, zero static specifiers measured), so pair it with Q5.4 rather than relying on it.
4. New small guard (e.g. `scripts/verify-autoloader-paths.mjs`, no build needed beyond dist/): for every
   `manifest.tags` value, assert `dist/web-components/<value>.js` exists and that the file registers the
   mapped tag (string-literal search, the same technique verify-consumer-sideeffects uses). That is the direct
   assertion of the BASE + basename contract the fold could have broken, and it is a pure dist read. It is the
   autoloader's analogue of `verify-react-wrappers.mjs`, which already does exactly this for React's
   specifiers. Measured today: 96 tags over 93 unique module basenames, ALL 96 resolve to an existing
   `dist/web-components/*.js`, and the one facade with no manifest tag is `remote` (deliberately outside
   register-all, see config/vite/web-components.ts splitConfig).
5. `verify:blocks` is already the real autoloader exercise. Do not duplicate it; instead give
   `apps/docs/public/autoloader-demo.html` a load test (a bare playwright project, or fold it into the docs
   `verify:preview` path) and FIX its PerformanceObserver regex from `/kitn/elements/` to
   `/kitn/web-components/`. Cheap, and it converts a shipped visual bug into a guard.
6. Lowest value / highest cost: a Node-side probe of `./state` and `./wire`. They are aggregate by contract and
   covered by `verify-cdn-entries`; a size ceiling there mostly guards a decision already pinned by that
   contract.
